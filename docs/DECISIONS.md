# 关键决策

MVP 阶段有意收窄的取舍。每一条都是"知道还有别的做法，但这一版不做"，而不是没想到。详细的状态机与边界见 [`PROJECT-CONTRACT.md`](PROJECT-CONTRACT.md)。

## 架构与部署

| 决策 | 取舍理由 |
|---|---|
| 一个 Spring Boot 模块化单体 | 按领域分包、保持边界清晰，但不付微服务的分布式事务与运维代价。真要拆，包边界就是拆分线。 |
| 共享数据库、共享表，所有业务表带 `tenant_id` | 租户数量少、隔离要求不极端时最省运维。写路径的 `tenant_id` 只来自登录上下文，不接受请求体传入。 |
| 一个 `sys_user` 固定属于一个租户 | 不支持登录后切租户。省掉了"当前租户"这一整类状态与越权面。 |

## 数据表达

| 决策 | 取舍理由 |
|---|---|
| 金额用 Java `Long` + 数据库整数，单位为分 | 禁止浮点与以元为单位的小数列，避免累加误差与对账偏差。 |
| 时间统一 UTC 存储，前端按时区展示 | 取当前时间必须走注入的 `Clock`，不用 `LocalDateTime.now()`，否则在非 UTC 机器上售卖窗口会整体偏移。 |
| 主键用雪花 ID | 单调递增便于按主键排序与分页，且不暴露连续可枚举的业务序号。 |

## 交易

| 决策 | 取舍理由 |
|---|---|
| 一个订单只包含一个场次、一个票档 | 去掉购物车与多行订单后，库存扣减与退款回补都是单行操作，不变量好证明。 |
| 只做模拟支付，不接三方收单 | 支付渠道的价值在对接文档而不在设计。用一个可控的成功/失败开关，把精力放在幂等与状态机上。 |
| 无座票，一票一码 | 不做座位图与选座锁位，票券只有"未用/已用/作废"三态。 |
| MVP 只做整单退款 | 部分退与按张退会让库存回补、票券作废、金额分摊都变成多分支，收益不在核心链路上。 |
| 库存先做 MySQL 条件更新基线，再叠加 Redis Lua 预扣 | 正确性由数据库保证并可测；Redis 只是前置过滤，对账以 MySQL 为准。 |
| 关单用 RabbitMQ 延迟消息 + 数据库扫描兜底 | 消息可能丢或延迟，扫描保证最终一定关；两条路径都用条件更新做幂等。 |
| 领域事件走 Outbox + Inbox | 业务状态与事件写在同一本地事务，消费端按事件 ID 去重，不用分布式事务。 |

## 后台能力

| 决策 | 取舍理由 |
|---|---|
| 审批用 `review_status` + `audit_operation_log`，不引流程引擎 | 只有"提交/通过/驳回"三个动作，没有会签与多级节点，流程引擎的配置成本换不来收益。 |
| 报表直接查事实表，强制带时间范围 | 数据量在 MVP 规模内，建实时数仓是提前优化。时间范围必填是为了防全表扫。 |

## 明确不做

真实收单与分账、选座与有座票、一单多票档、购物车与优惠券、登录后切租户、部分退款与改期、工作流引擎、实时数仓与离线 ETL、微服务拆分、分库分表、渠道分销、会员体系。

完整清单见 `PROJECT-CONTRACT.md` 第 6 节。新增能力的流程是先改契约文档、再改代码。
